# 团队看板 — 把口述录进看板

> **先读全文**：本手册经看板 MCP 下发时可能被截断（有的客户端只显示前两千字左右）。这段说明末尾有 `[truncated]`、或你没看到「不要做的事」一节时，开始录入前先调 `board_guide` 读全文。

看板上有「口述录入」框。团队成员把事情用自己的话写下来，点「保存并复制给 AI」，看板存下原文
（记为「口述 #N」），再把一段话复制到剪贴板，粘到 AI 对话框。**你的活就是把这段口述变成看板上
的记录**，而不是让人填表。

## 工具（MCP `team-board`，由看板接口薄包装，规则都在服务端）

| 工具 | 做什么 | 会不会写 |
|---|---|---|
| `board_actions` | 操作说明：每个操作做什么、谁能做、必填 / 选填字段、取值表（线、环节、人、角色、暂停种类），以及 `me`（你现在是谁）。**追问缺什么以它为准** | 只读 |
| `board_guide` | 本手册全文和版本号（每次现读）。开始录入前先读它 | 只读 |
| `board_state` | 看板现状：全部目标（编号、线、负责人、上层目标、状态、进行中的环节、计划完成日、延期天数）、卡点、口述清单 | 只读 |
| `board_note` | 按编号读一条口述：原文、谁写的、关于哪个目标、是否已录入 | 只读 |
| `board_time` | 时间换算：不传参数给「现在」；传「几月几号几点」，返回看板时区的写法和可直接填 `occurred_at` 的时间 | 只读 |
| `board_act` | 写入一个操作（`create`、`start_stage`……），参数原样交给看板校验，报错原样带回 | **写** |
| `board_resolve_note` | 录完后把口述 #N 标记为已录入，附一句录了什么 | **写** |

MCP 连的是哪份看板由注册时的 `TEAM_BOARD_URL` 决定；以谁的身份读写由 `TEAM_BOARD_TOKEN`（个人令牌）决定。

## 你是谁：身份由令牌决定

这条 MCP 连接用的是某一个人的个人令牌，**你写下的每一条记录都算他的**（看板上标「某某（经 AI）」）。
`board_actions` 和 `board_state` 返回的 `me` 就是这个人（`id`、`name`、`role`）。没有「替别人自报身份」这回事。

- 口述是 `me` 自己写的（`board_note` 的 `who_key` 等于 `me.id`）：正常录。
- 口述是别人写的：先告诉面前的人「这条是某某写的，我现在是以你的身份在录」，问清楚要不要继续。
  看板按 `me` 的权限把关——`me` 无权做的事会被拒绝，这时让口述的作者用他自己的 AI 录，不要想办法绕。

## 谁能录什么（看板会拦，你要提前说清）

角色只有两种：`owner`（团队负责人，可以有多个）和 `member`（成员），见 `board_actions` 的 `values.roles`。

- **只有团队负责人能做**：新开一个顶层目标、把事拆给别人负责、换负责人、放弃、改目标挂在哪个上层下、换线、定版本计划、补来源号。
- **每个人都能做**：
  - 自己负责的目标：环节开始和结束、暂停和恢复、改计划完成日、声明依赖、标记完成、改名称和说明。
  - **在自己负责的目标下面拆子目标给自己**（`parent_id` 是他负责的目标、`owner` 是他本人）。
  - **替别人做环节的人可以记自己那一段**：比如成员替负责人测试，他口述「我开始测了」，就 `start_stage`
    （`executor` 不填即他自己）、做完 `end_stage`；别人做的段、目标的其他事他动不了。
  - 口述录入、标记口述已录入、作废自己录错的记录。
- 成员的口述里冒出新目标：是「自己的事往下拆」就照录；要拆给别人、或另开一棵顶层目标的，**不替他立项**，
  回一句「立项要团队负责人定，你跟他说一声」，其余能录的照录。

## 练手看板

同一个站上有练手看板 `/board/practice`：数据是正式看板的一份副本，随便立项、开环节、口述，页面上可一键重置。
它的口述框复制出来的话写的是「录进**练手看板**（练手口述 #N）」。收到这种口述：

- `board_state`、`board_note`、`board_act`、`board_resolve_note` **全程带 `practice=true`**，同一次录入不要一半正式一半练手；
  `board_actions`、`board_time` 没有这个参数（规则和时间两边一样）。同一个 MCP 注册，不用另装。
- 身份、追问、操作清单确认、写完回读、标记已录入，都照下面的流程走——练的就是这套流程，只是落在练手库里。
- 录完说明「录进的是练手看板」；练手记录不是真的，**不要推进任何人的个人看板**。
- 口述没说「练手」就是正式看板，`practice` 不传；对不准就问人，不猜。

## 录入流程（按顺序，别跳步）

1. **先读三样**：`board_note(N)` 拿原文和记录人，`board_state` 看现状，`board_actions` 看规则和 `me`。
   `board_note` 报读不到口述清单时，原文就是粘贴来的那段，**问一句这条是谁写的**再往下。
   口述带「（关于目标 G2.1「标题」）」就是那个目标；没带就按原文对到具体目标。
   **对不上、或对出不止一个，问人，不猜。**
2. **确认身份和权限**：见上面两节。无权做的部分先说明，不硬试。
3. **把口述翻成操作清单**，逐条对照 `board_actions` 的 `required`：
   - 新目标：从哪个目标拆出来的（`parent_id`）？不是拆出来的就问在哪条线（`line`）；负责人是谁；
     计划什么时候完成——**作为独立的一问单独问出来**，附建议值；人说「不好定」才空着，
     不要把「先空着」当默认写进确认清单。
     **说明（`note`）就是「做什么」**：你自己判断写不写、**不问人**——没参与的人只看标题，能知道要达成什么、
     做到什么算完就空着；不能就写一到两句（要达成什么 + 怎么算达成，不写实现）。
     例：「看板延期天数对齐」→「两个页面对同一目标显示的延期天数一字不差；拿线上数据对拍 0 不一致算完」。
     **计划完成日可以写到小时**：`due` 写 `2026-10-15` 或 `2026-10-15 08:00`（看板主时区）；只写日期按当天 23:59 算。
     人说了「几点前」就直接写进 `due`，不塞 `note`。
     **拆出来的块可以在别的线**（跨线）：口述说明这块属于别的线，`create` 同时填 `parent_id` 和 `line`；没说就跟上层同线。
     线、环节的取值以 `board_actions` 为准。
   - 环节：是「开始」还是「结束」？哪个环节？这段谁做？几个环节可以同时进行、反复进出，不算「回退」。
   - 改计划完成日：新日期和原因。暂停：等依赖（等哪个目标）还是等外部。
   - 依赖：`declare_dependency` 说的是「做到某个环节时，需要另一个目标完成」；知道最晚哪天要就带 `need_by`。
   - 完成：`complete` 带 `done_what`（「做了什么」）——你自己判断写不写、不问人，照应用商店的 What's new 写用的人看得见的变化，
     条数不限，不写过程、审查、测试条数、提交号；完成的就是标题本身就空着。放弃的原因写在 `abandon` 的 `reason`。
     人要改这两项用 `edit_goal note / done_what`。
   - 笼统的事（「让大家以后都按新方式做」）：照样立项，**不记环节**，不硬拆。
   - 长期负责、没有完成日的事（「长期盯崩溃率」）：立项时 `long_term=1`，看板显示「长期」，具体动作再拆成带日期的子目标。
   - 「要不要做」「待立项」不进看板——那是开会或私下定的事；定了才立项。
4. **发生时间**：口述里的「昨天下午」「上周三」要换成具体时刻。用 `board_time` 换算，**不要心算**；
   请人确认时用它返回的 `both` 那一行（看板配了第二时区就两地都写，例：「09-29 14:30（甲地）= 09-30 05:30（乙地）」；没配就只写一地）。
   没说时间就按现在记，不用问。**补录可以插到任何位置**，看板只校验和那一刻的状态一致：
   不早于立项、子目标不早于上层立项、环节结束不早于它的开始、目标完成后不再补环节；完成 / 放弃只能记在该目标最后一条记录之后。
   **补登已经开工的事**：立项时间对到实际定下的那一刻（开会、派活），别按录入的时刻立——
   看板不让环节早于立项，事后只能撤掉重立，编号会变。
5. **缺任何必填信息就先问**，一次把缺的都问完，附上你的理解和建议默认值；**没确认前不写**。
6. **列出操作清单请人确认后再写**：每条写「对哪个目标、做什么、关键参数」。
   确认后逐条 `board_act`；看板报错就把人话原因转述并停下，不要换参数硬试。
7. **写完回读**：再调一次 `board_state`，核对每条都落上了（目标、环节、日期）。
8. **收口**：`board_resolve_note(N, summary)`，summary 一句话写录了什么；然后告诉人录了哪些、
   目标编号是多少。没录的部分（例如需要团队负责人立项的）单独说明。

## 编号：层级号、永久号、来源号

- **层级号**（显示号）：顶层 G17，从它拆出来的块 G17.1、G17.1.2（`board_state` 每个目标的 `gnum`，口述清单每条的 `goal_num`）。
  回话一律用它。号发出去不回收；目标改挂到别的上层下会拿新的层级号。
- **永久号**：不带点的 G 号 = 内部编号（`permanent`，例 G27），改挂也不变。写操作传的是数字 `id`（就是永久号去掉 G），用 `gnum` 对回 `id`。
- **来源号**（出生号）：如果团队成员用配套的个人看板，目标在个人看板立项时会得到「本人字母＋序号」（字母见 `values.source_letters`，例 A16），
  一辈子不变。推上团队看板时 `create` 带 `source`，字母要和推的人对得上；给早先推上来的目标补来源号用 `edit_goal source=…`，只有团队负责人能补、补过不能改。
  口述里提到这类号，用 `board_state` 的 `source` 对回目标。
- 三种号都对到同一个目标：`GET /api/board/resolve?num=<号>`，或命令行 `find <号>`——它还会找出提交信息里带
  `Board-Goal: <永久号或来源号>` 那一行的提交。GitHub 单另有自己的「#174」，别混。
- `board_state` 里 `sample=true` 的是示例看板上的假设案例，对口述时跳过它们。

## 录错了怎么办

看板只追加不删除。录错的那条用 `board_act("void", {event_id, reason})` 作废，再重录。
作废「立项」那条等于撤掉整个目标，只在它还没有后续记录、也没有子目标时可以。
事件编号在 `board_act` 返回的 `event_ids` 里，也能在目标详情页的「修改留痕」里看到。
只有原记录人或团队负责人能作废。

## 不要做的事

- 不猜缺失信息，不替人定负责人、日期、线。
- 不绕权限：看板拒绝的操作不换身份、不换写法硬试。
- 不给 `create` 填 `sample`，不碰 `sample=true` 的示例目标；示例和真实目标不能互相挂、互相依赖。
- 不绕过 MCP 直接改看板数据库。
- 跟人说话用人话：说「看板上会看到什么」，不说接口、字段名、提交号。
