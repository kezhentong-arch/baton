# 个人看板手册 — 把零散的 AI 对话归进主线

> **每个对话一开始**：先把这个对话归到线 / 目标 / 环节，说一句并记开工（闲聊问答不记），规则见第一节。
> **先读全文**：有的客户端只显示这段说明的开头（例如前 2048 字）。这段末尾出现 `[truncated]`、或你没看到第七节时，开始归类或记录前先调 `personal_board_guide` 读全文。

为什么要记：一个人一天开十几个 AI 对话并行，每个对话的工作都归到一条线、一个目标、一个环节，打开看板就知道主线上每件事到哪了。
连了团队看板时，个人看板也是本人那部分团队看板的信息来源：攒着的改动收尾时经本人点头，由 AI 批量推上去。

线和环节由本人在配置里定，取值以 `personal_board_actions` 的取值表为准（默认四条团队线加一条个人线；五个环节：业务、产品、UI、开发、测试）。
不能严格归入某个环节的记「未分环节」（`stage` 不填）。**个人线**（取值表之外看 `personal_board_state` 里线的 `personal` 标记）不拆环节、永远不推团队看板。

工具看工具列表；写操作的参数与取值表以 `personal_board_actions` 为准；本手册全文 `personal_board_guide`。
记录都带 `task`（这个对话在做的事，几个字）和 `tool`（`claude` / `codex`）；`occurred_at` 不填就是现在，补录才填（带时区的 ISO）。
写入带 `request_id`（UUID），结果不明时用同一编号、同一参数重试，要改参数先读现状；看板连不上就报错，不在别处另记。

## 一、对话一开始：归类（AI 先判断，拿不准才问）

1. 读 `personal_board_state`：各条线里进行中的目标和下一步；`points_due` 有今天到点或已过期没做的点状任务就按第五节提醒。
2. 从开场白判断线、目标、从哪个环节开始，**说一句**（例「这个对话我记在 G2 新用户引导改版 · 开发」）。
   人不反对就记 `log kind=start`；该环节还没开着就一并 `stage_start`（第一次进新环节先问，见第三节）。
3. 对不上任何目标、或对出不止一个：问人，不猜。闲聊、问答、与目标无关的事不记。
4. 新目标用 `goal_create`，立项即发**出生号**（本人字母＋序号，例 A19；一辈子不变、用过不再发）。
   团队线下的目标收尾时推上团队看板（带出生号），推完 `goal_update gnum=G…` 换显示号，出生号仍能找到它；提交信息里可以写这个号。
   - **计划完成日单独问一句并附建议值**：人说「不好定」才空着，不把「先空着」当默认。可以写到小时（`2026-10-02 08:00`，主时区）。
   - **「做什么」AI 自判写不写，不问人**：没参与的人只看标题能知道要达成什么、做到什么算完就空着（点状任务一律不写）；
     不能就带 `what` 写一到两句：要达成什么 + 怎么算达成（能验证的判据，不写实现）。
     例：「引导改版」→「新用户三步内添加好第一只宠物；注册到添加完成的比例到 60% 算完」。
   - **落地与持续维护分开立项**：落地类目标做到 v1.0 能用就收口；之后对工具 / 手册的升级维护是独立的**长期行**
     （`long_term`，不挂在落地目标下；不想让它上团队看板就在立项后把立项记录 `sync_mark status=skip`），落地目标才能按时完成。

## 二、记到多细

- **开工**一条（`kind=start`）。
- **每出一个看得见的结果**一条（`kind=result`）：页面跑通、文档定稿、一轮测完、方案确认；不逐句记，一小时通常不超过两三条。
- **收尾**一条（`kind=wrap`）：这一段做了什么、下一步。
- **沉淀**一条（`kind=digest`，图上金色点；绿色专指目标完成）：经验或规则写进了手册 / 知识库就记，文字写「手册 x.y.z：沉淀了什么」。
  记在对应工作的目标上；本人有手册类长期行的记在那一行。**只有长期行才带 `version`**，普通目标带了会被拒。
- 环节开始 / 结束用 `stage_start` / `stage_end`；可以多个环节同时开着，反复进出照实记，不算回退。
- 目标的「下一步」变了就 `goal_update next_step`，开工时据它列今天的事。

**完成与版本收口时写「做了什么」**：照应用商店的 What's new，用简洁通俗的话写用的人看得见的变化，一条一行，
不写过程、审查、测试条数、提交号；AI 自判写不写，完成的就是标题本身就空着。只在完成 / 收口时写一次，人要改再 `goal_update what= / done_what=`。
- 普通目标：`complete` 带 `done_what`（开着的环节一起结束）；放弃的在 `status=abandoned` 的 `reason` 写为什么。
- **工具类长期行**（持续维护某个工具）：改动要人看过才算，每轮在那一行开「开发」→「测试」，人认了才结束环节，
  再记一条 `release`（`version` 写新牌、`text` 写这版做了什么），**版本牌**随之换掉、详情页「更新日志」多一版。
  版本号按改动大小：修 bug、小调整升小版本（v1.1 → v1.1.1）；功能性大改才升下一版（v1.2）；开工时 AI 说一句算哪个号，人定。
- **手册类长期行**：改一条写完就算，记 `digest` 带 `version`（例「手册 1.2.0」），版本牌一并换。
- 版本牌永远是号最大的那一版。不推团队看板的行，它的环节记录不标「未推」。

## 三、环节把关

- **第一次**进新环节，先把上一环节的产出和缺口列给人（「产品这段做完了吗：方案已定稿、你看过——缺 X。要进开发吗？」），
  人说可以才 `stage_start`；半成品可以进但人要知道缺什么，残次品不进。往返（测出问题回开发、改完再测）不用问，照实记。
- 开工和收尾时对每个开着的环节核一遍，列「做到了什么 / 缺什么」，问要不要结束或进下一环节；
  看到人已经在干下一段的活却没说，当场提一句。
- 不替人定目标归属、环节、线；不猜缺失信息。

## 四、收尾：说「收工 / 收尾」时

0. 先问「这轮有没有值得沉淀进手册的经验」，列候选；人点头后才写，写进去了按第二节记 `digest`。
1. `personal_board_state` 看今天，写一句汇总记 `wrap`。
2. **没连团队看板**（`header.team_board` 为 false）到此结束；`personal_board_pending` 为空是正常的，不要提「未推」。
3. 连了团队看板：`personal_board_pending` 列「未推」记录，按目标分组写给人看（目标、做什么、发生时间）。
4. 人点头后，**逐条经团队看板自己的 MCP 推**（它的写入工具：`team-board` 这个 MCP 服务的 `board_act`；操作名与参数以团队看板的操作说明为准，下表是通常的对应）：

   | 个人看板记录 | 团队看板操作 | 带什么 |
   |---|---|---|
   | `goal_create`（团队线） | `create` | 标题、负责人、线、上层（团队看板上的 id）、`due`（原样带时刻）、`occurred_at`、`source`（出生号，未推清单的 `birth`）、`note`（「做什么」，未推清单的 `goal_what`；空着不带） |
   | `stage_start` / `stage_end` | `start_stage` / `end_stage` | 团队看板上的目标 id、`stage`、`occurred_at` |
   | `due` | `change_due` | 目标 id、`due`（原样带时刻）、`reason`（记 due 时就把原因写进 `reason`） |
   | `abandon` | `abandon` | 目标 id、`reason` |
   | `complete` | `complete` | 目标 id、`occurred_at`、`done_what`（未推清单的 `goal_done_what`；空着不带） |
   | `summary`（已推目标改了做什么 / 做了什么；同一目标只留一条） | `edit_goal` | 目标 id、改「做什么」带 `note`、改「做了什么」带 `done_what`（清空就显式带空字符串） |

   团队看板上的目标 id 从团队看板的现状里用 G 号对回并核实，**不用个人库内部的 goal_id**（两套编号不同）。
5. 推成功后 `sync_mark`（`entry_ids`、`status=pushed`、`team_ref` 写返回的事件号）；新立项拿到 G 号后 `goal_update gnum=G…`。
   团队看板拒绝就原样转述，那条留在未推，不硬试。
6. 人说某条不推 → `sync_mark status=skip`，或 `void` 作废重记（作废「完成」不会把目标改回进行中，要改用 `goal_update status=active`）。
7. 环节真的切换时，也当场问一句要不要先把这几条推了。

一次收尾由一个对话负责，其他对话照常记录，不同时推同一份清单。个人看板自己不写团队看板，唯一写入口是团队看板的 MCP。

## 五、口述与点状任务

**口述框**：页面口述框保存后会复制「请把下面这段口述录进我的个人看板（口述 #N）…」。收到后读 `personal_board_state` 的口述清单拿原文
→ 对到目标、环节 → 缺什么先问 → `personal_board_act` 记 → `note_resolve` 写一句记了什么 → 告诉人记了哪些。

**点状任务**：只在某个时间点做一次的事（例：每月 1 号给外包结款）。时间线上到点才出现空心大点，做完变实心，
过期没做的标红「过期 N 天」。**不推团队看板、不开环节、不填计划完成日**（看板会拦）。
- 建：`goal_create` 带 `point_at`（第一次的时刻）、`point_zone`，每月的再带 `repeat=monthly`。先问清日子、挂哪条线；
  没说几点 AI 定一个并说出来；配了两个时区时问清按哪边的钟点（跨夏令时不会错一小时），没说按主时区。建完把下一次的时刻写给人看。
- 勾掉：人说「Y 做了」就 `point_done`（不指明哪一次就勾最早那次没做的）；勾错 `void` 那条。
- 提醒：开工时 `points_due` 有今天到点或已过期没做的、且 `reminded_today` 为 false，回复里提一行（照它给的 `say`），
  不追问，再记 `point_reminded`；一天只提一次，过期没做的每天提一次。
- 改日子用 `goal_update` 改 `point_at` / `point_zone` / `repeat`；不再做了 `goal_update status=abandoned`。

## 六、号的写法

- **出生号**（字母＋序号，例 A19）是目标在个人看板上的身份，推上团队看板以后仍然认；显示号在推完后换成团队看板的 G 号。
  页面上两个号都显示（`A19 · G2.3`）。对人说话、写提交信息时用出生号最稳，它不会变。
- 团队看板的层级号（G2.3）表示位置，改挂上层会变；提到时带上标题，别只甩一个号。

## 七、规矩

- 请人确认具体时刻时用 `personal_board_time` 换算，配置了两个时区就两地都写（它返回的 `both`），只配一个就写一个。
- Claude Code、Codex 的对话都照本手册记；多个对话写同一份看板，靠每条记录的 `task` / `tool` 区分。
- 对人说话用产品语言：说「看板上会看到什么」，不说字段名、提交号。
- 练手模式（`PERSONAL_BOARD_PRACTICE=1` 起的 MCP）里的记录不是真的，别推团队看板。
- 改了看板的代码后，开着的对话里 MCP 还跑旧代码，新对话才生效。
