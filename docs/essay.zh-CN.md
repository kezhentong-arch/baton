# AI 写得飞快，你的团队为什么还是这么慢？因为交接才是最大的 bug

*一棒到底：人人都有 Claude Code 之后，小团队怎么协作*

曹通

## AI 写得飞快，为什么事情还是做得慢？

用 AI 干活的人，大概都有过这种感觉：AI 写代码、出页面、跑测试，快得惊人。可一件事从「想做」到「真的用上」，并没有快多少。

我们团队从第一天起，所有开发都是在终端里用 Claude Code 完成的，照理说应该很快。可前段时间我复盘我们的「矩阵设备社媒自动增长系统」，发现它的上线比计划慢了很多。

先说这套系统是什么。顾名思义：它用本地部署的 GUI 模型，像人一样看屏幕、点屏幕，自动操作一整排设备，在社交媒体上做运营和增长，可以给任何产品做增长。下文简称增长系统。它分三部分：给人用的网页端，在设备上自动操作的执行端，还有执行端依赖的底层设备控制能力。

计划里写着「这周投入使用」，一连几周都没做到。再往前看，我们的 App 从开工到能上线，也比预想的久得多，最后还在测试上卡了很久。

Claude Code 没问题，人也都很努力。想了很久，我的结论是：问题出在我们一起做事的方式上。

## 以前的做法：接力赛

软件行业几十年的标准做法，是分环节：一个人想清楚业务、写需求，交给下一个人开发，再交给第三个人测试。像接力赛，每过一棒，换一个人。

我们以前也是这样。吃过的亏，全出在交接棒上：

- **交之前，不知道该给什么。** 我把一件事交给负责开发的同事时，很多时候并不知道要给他哪些信息。为了交接，我花大量时间写需求、补文档，还是会漏。因为很多东西，写的人自己都意识不到要写。
- **缺什么，要等对方踩了坑才知道。** 做到一半发现缺东西，退回来补，补完再交回去。对方手上还有别的事，要排队。一来一回，几天就没了。
- **明明给了，还是会丢。** 增长系统的网页端和执行端怎么联动，其实都在我当时做的那套完整原型里。原型是能点、带功能的，不是几张图。可交接之后，这一块还是丢了，直到最后才发现没做。它正好落在两棒之间。
- **测试堆到最后。** 一大批做完才交给测试，问题全压在收尾。最后那一点，比预估的难得多。
- **所有人排队等同一个人。**

每个人都在认真对自己那一棒负责：把上游给的接住，把自己这段给下游交代清楚。可大量的脑力，就花在了「交代」上。

还有一点要说明。东西还小的时候，这些问题并不明显：一个刚起步的小样，从零开始一点一点往上加，用接力的方式也还过得去。可一旦面对的是一套已经成型的复杂系统，要交代的东西成倍变多，交接就成了最大的麻烦。

## 为什么有了 AI，这套就不灵了

接力赛的分工，在以前是有道理的。写代码、做设计、做测试，每一样都要练很多年，一个人干不过来，只能分给不同的人。

但现在，具体的活大多是 AI 在干。一件事里最费劲的部分，早就不是「把它做出来」，而是**「知道具体要怎么做」**。

这时候再按老办法分工，就等于在「知道怎么做的人」和 AI 之间，多隔了一个传话的人，一个二传手。

而且在 AI 时代，这种转手比以前更伤。

以前交接，是人写给人看。现在每个人都在用 AI：我把想法讲给我的 Claude Code，它帮我写成需求文档。三句话的事，它能写出三页，里面还可能掺进我根本没说过的东西。我得一条一条核对，核对完交给负责开发的同事。他再让他的 Claude Code 去读这三页、去实现，它又会加上自己的理解。

一件事就这样在「人、AI、人、人、AI」之间来回转手。每转一次，信息被放大一次，走样一次，还可能混进一次 AI 的幻觉。到最后做出来的，和最初想要的，中间隔了好几层。

很多团队的做法是：分工不变，给每个环节的人都配上 AI。每一棒确实跑得更快了，可交接棒的时间一点没少，交接的损耗反而更大了。我们一开始就是这样，所以才会「AI 很快，事情很慢」。

## 新做法：一棒到底

我们把规矩改成了一句话：**一件事，谁发起，谁负责到底。**

一件事定下来要做，就交给一个负责人。这个人用 Claude Code，尽量自己从头做到尾：想清楚要达成什么，设计，开发，测试，直到它真的用起来、达到当初的目标。棒，不交出去。

有三点要说清楚。

**五个环节，每个人都能做。** 我们把一件事分成业务、产品、UI、开发、测试五个环节。环节说的是「在做什么」，不是「谁来做」。有了 Claude Code，一个人可以把五个环节都做下来。我自己不是工程师出身，现在我负责的系统，产品、UI、开发、测试，都是我用 Claude Code 做的。

**对结果负责，不对过程负责。** 负责人不用对上游交代，也不用对下游交接负责，只对一件事负责：它最终有没有做成。脑子全部用在把事情做成上。

**环节来回交替，不算返工。** 一个人做到底时，不是产品做完再做开发、开发做完再测试，而是交替着往前走。测出五个问题，回头改开发，或者干脆回头改产品，同时接着往下测。这和以前「缺了东西退回给上一个人、来回等」完全是两回事。

拿我们自己举例。做团队看板的时候（后面会讲它是什么），产品、UI、开发是同时往前推的：我看着做出来的页面提意见，回头改方案、改 UI，开发同时在继续。没有「做完一段再交给下一个人」，也没有谁在等谁。第一版上线后的一天之内，两个看板加起来又迭代了十多个小版本，每一版都是我提出、我用 Claude Code 做、我验收、我发布。

两种做法放在一起比：

| | 接力赛 | 一棒到底 |
|---|---|---|
| 会不会漏 | 交给下一棒前要写成文档，花大量时间还是会漏 | 东西一直在自己脑子里，不用写给别人，也就不会漏在交接里 |
| 信息会不会走样 | 人和人、人和 AI 之间来回转手，每转一次放大一次、走样一次 | 只有「我」和「我的 Claude Code」这一层 |
| 多久知道缺什么 | 等下一棒做到一半踩了坑才知道 | 做到哪、发现哪，当场补上 |
| 补一次要多久 | 退回去补、再交回来，对方还要排队，一来一回好几天 | 自己回头改，同时接着往下做，几分钟到几小时 |
| 心思花在哪 | 把自己这一棒交代清楚 | 把整件事做成 |
| 测试 | 一大批做完才测，问题全堆到最后 | 边做边测，最懂这件事的人自己测 |
| 等人 | 每一棒都要排队 | 大部分时间不用等别人 |

## 快，才是目的

换掉接力赛，为的不是省事，是快。

一个功能好不好用，一个设计合不合理，坐在那里想是想不出来的。最可靠的办法只有一个：用最快的速度做出来，拿到市场和用户的反馈。哪怕只是自己用上一用，得到的反馈也比开十次会多。

做出来，用一用，改一改，再做。这样一轮一轮转得越快，就越接近一个成熟的产品，也越早知道当初定的目标到底对不对。

所以我们给自己定的节奏是：每条产品线至少每周迭代一轮，每个人自己的小闭环，一到三天一轮。先跑起来，不做大活。计划定得紧一点，不怕延期；延期了再看原因，用它倒逼速度。

## 同一件事，两种做法

回到增长系统。前面说过，它有网页端、执行端、底层设备控制能力三部分。

**当时实际是这么做的：** 我做完原型、写好需求，交给负责开发的同事。他把三部分全部开发完，再交回来测试。结果网页端和执行端的联动丢在了交接里，到最后才发现缺了这一块。「这周投入使用」就这样一周一周往后拖。

**按一棒到底，会这么做：** 拆成三块，每块一个负责人，各自从产品做到测试。

- 网页端：我自己做到底。
- 执行端：也是我做到底。
- 底层设备控制能力：负责开发的同事整块负责。要做成什么样、怎么做，他自己定。

这样拆有两个好处。

第一，网页端和执行端都在我一个人手里。我做网页的时候，自然知道执行端要回传什么，联动这一块不用向任何人交代，也就不会丢。

第二，谁等谁一清二楚。执行端的开发要等底层能力，网页端不用等。所以负责底层的同事会把「对外接口长什么样」尽量提前定下来；我在等的这段时间，先把网页端做完、把执行端的方案想清楚。没有人闲着，也没有东西落在两个人中间。

## 一个人开着十几个终端，怎么不乱：个人看板

一棒到底之后，交接的麻烦没了，新的麻烦来了：**Claude Code 太快，人跟不上。**

一个人一天会开十几个 Claude Code 终端：这个在写页面，那个在改接口，还有一个在跑测试。而且一个目标常常不是一个终端就能做完的，要好几个终端同时做，或者一个接一个地做。终端一多，人很容易绕晕：到了晚上，每件事做到哪了，自己都说不清。

为此我们做了第一个工具：**个人看板**。它管的是你和你的 Claude Code。

- **每个终端，一开始就自己归到一个目标、一个环节上。** Claude Code 先说一句「这个终端，我记在某某目标的开发环节」，你不反对就记下了。你什么都不用填。同一个目标开了多少个终端，最后都汇到看板上的同一行。
- **出了看得见的结果，才记一笔。** 页面跑通了，文档定稿了，一轮测完了。打开看板，每件事到了哪一步、下一步是什么，一眼看清。
- **第一次进一个新环节，要你点头。** 方案还没定完你就想让它写代码，它会先把缺什么列给你，再问一句要不要进。Claude Code 跑得快，但从「想清楚」到「动手做」这一步，方向盘在你手里。至于测出问题回头改，不用问，那是正常迭代。
- **每个目标只写一句「下一步」。** 不设优先级档位，先做哪件，自己看着排。

用了它之后，我每天早上打开看板，就知道昨天那十几个终端各自把事情推到了哪，今天该从哪接着做。

## 一棒到底，不是一个人单干

这套做法最容易被误解成「各干各的」。不是。人和人之间照样要配合，只是配合的地方变了：以前是一件事在几个人手里传，现在是一件大事拆成几块，每块有一个人负责到底。

举个我们正在做的例子。App 要加一项新功能，牵涉 App 本身、后端和管理后台。这件事由我发起，我把「要达成什么」想清楚，然后拆成两块：后端和第三方接入，交给负责后端的同事；App 里从产品、UI 到开发、测试的全部，交给负责 App 产品的同事。两个人各自整块负责。

这里面有几条规矩。

1. **先对齐，再投入。** 小团队精力有限，做什么、先做什么，要放在一起定。要不要做，在周会上、在私下聊天里商量；定了，才立项。
2. **我只做了开头，但这件事仍然归我负责。** 两块各有负责人，他们各对自己那块的结果负责；整件事最后有没有达到目标，仍然由我负责。
3. **整块交出去，怎么做由接手的人定。** 我举的例子只是参考，不是指令。要做什么、怎么拆、要不要再找人帮忙，都由他自己定。
4. **负责到底，不等于每一步都亲手做。** 自己做不了的部分可以请别人做，但做回来的东西，负责人要能验收。这一步省不掉。
5. **新上手的人，事先说好在哪几个点停一下。** 这一条不是每次都要。只有当接手的人第一次这样整块负责、还不熟的时候，才约好中途停几次：比如产品方案做完，我看一次；UI 做完，我再看一次。看一次是验收，不是交接，看完再定下一步怎么走，免得把人硬推到一个还没准备好的环节上。等他熟了，这些停顿就取消，只留最后的验收。
6. **请人帮忙，负责人管教会。** 请别人一起开发或测试，负责人要把标准讲清楚，并负责把对方教会。
7. **每个环节，由本来干这行的人兜底。** 一棒到底不是说专业不重要了。团队里每个人都有自己原本的专业：有人本来做产品，有人本来做开发，有人本来做设计和测试。在这套做法里，谁的专业是什么，谁就给那个环节兜底。比如在我们团队，业务和产品由我兜底；开发、后端和线上服务器，由负责开发的同事兜底；UI 和测试，由本来做这一块的同事兜底。别人做到这个环节遇到拿不准的，可以去问他，可以拉他一起做；实在推不动，由他接住。但兜底只是保险，不是说这个环节默认归他做。

## 不交接了，别人怎么知道进展：团队看板

第二个新麻烦也跟着来了。以前靠交接，大家自然知道一件事进行到了哪。现在不交接了，谁在负责什么、做到哪、卡在哪，别人怎么知道？

所以有了第二个工具：**团队看板**。它管的是人和人。

- **所有目标在一条时间线上。** 每个目标谁负责、拆成了哪几块、每个环节花了多久、卡在哪，一眼看清。上面那个「App 加新功能」的例子，在团队看板上就是一行大目标，下面挂着两块，各写着负责人。
- **谁在等谁，提前标出来。** 一块要等另一块做完才能往下走时，如果被等的那块预计完成的日子，晚于等它的那块需要它的日子，看板会提前提醒。不用开会问。
- **它是给每个人指路的，不是排名。** 每个人随时知道公司在推进什么、自己那块在整体里的位置。
- **用说的，不填表。** 要立一件新的事、要更新进展，用自己的话讲清楚，交给 Claude Code 录进看板；缺了什么，它会追问。我们希望每个人都像合伙人一样想事情，而把一件事完整讲清楚，本身就是这种思考。填表太机械，更像员工。

两个看板是分开的。个人看板细到每个小时、每个终端，只给自己看；团队看板上，每件事只留一行摘要。每天收工时，在终端里说一句「收工」，Claude Code 会把今天该让团队知道的变化列出来，你点头，它才同步到团队看板。

## 要付的代价

代价也要说清楚。

让不是工程师出身的人用 Claude Code 做开发，代码可能不漂亮。我们接受这个风险：在现在这个阶段，能跑、能验证，比架构好看重要。

另外，自己做也要留痕。哪怕从头到尾一个人，也照样记下每个环节的开始和结束。复盘时才看得清时间花在了哪。这件事交给个人看板，不用人操心。

## 它适合谁

适合：人不多、每个人都在用 Claude Code 这类工具干活、愿意对一件事的结果负责到底的团队。也适合一个人开着一堆终端做事的独立开发者，只用个人看板就够了。

不那么适合：必须严格分权审核的场景，或者团队成员还不愿意走出自己原来的环节。这套做法要求每个人都往前多走几步。
