# 产品与 UI 环节：文档与原型互相对照着定

两个环节合成一本：负责人做产品时，落点往往就是原型，两段交替重叠。但**两段各有出口，看板上分开计时**。

## 两条进路（出口一样）

| 进路 | 什么时候用 |
|---|---|
| **先文档后原型** | 想法已经成熟，先把需求写全，再做第一版完整原型 |
| **先原型后文档** | 一句想法、小迭代：盘现状 → 改原型 → 人看 → 定稿 → 更新文档 |

不管走哪条，**原型是锚**：有界面的内容，以负责人看过点头的原型为准去改文档，不改原型迁就文档。没有界面的内容，文档本身就是交付物。

## 产品这段：AI 做什么

- **先盘现状**：查现成的能力、页面和文档，别重造已有的东西。把「现在是什么」和「要改成什么」分开写；
  现状要标明是现状，不冒充规定（「目前每周发一版」不等于「必须每周发一版」）。
- **需求拆三层**：产品目标（必须满足）、沿用的既有做法（原样保留）、技术方案（只作参考，开发时定）。
  要负责人定的只有产品问题，附上建议。
- **写需求**：用户看得到的行为、业务规则、文案、通知谁。每条写「现在是什么 / 要改成什么 / 为什么」；不写对话口吻，不写实现细节。
- 文档带版本号，每次改动加一行版本记录。

### 产品出口

- 需求文档定稿，负责人看过并说可以；
- 每条都有「现在 / 要改成 / 为什么」，没有待定的占位（「这一节稍后补」不算定稿）；
- 受影响的产品文档已按定稿更新（有界面的，等原型定稿后一次改完）。

## UI 这段：AI 做什么

- 做本轮的原型：单文件网页，或在本地起一个能点的页面。改完截图给负责人看，他看着原型提意见，产品和 UI 同步改。
- **拿真数据的页面给人看，不出静态效果图**；示例要像真实使用的样子。已经有线上数据的，用它的副本在本地起。
- **先沿用验证过的做法，再谈改**；但沿用不是照搬，先想清这里是谁在用、怎么用。
- **人的意见先核实再改**：「问题」和「他建议的改法」分开处理，问题必改，改法给出判断；他看错了的，如实指出。
- **一个视觉信号只表达一个意思**：整行高亮已经表示「选中」，就别再用它表示「可以展开」。
- **一个东西要不要单独占一行，看它有没有上一层给不了的信息**：一对一的包含关系，只在上一层留个标记。
- 原型带版本号，每轮改了什么记下来。

### UI 出口

- 负责人看过原型并说可以（有截图，或他亲手点过）；
- 原型存到了团队找得到的地方（并入主线或固定目录）；
- 原型与文档一致。

## 用得上的经验

- **给别人看的材料，截图一律取自线上最新版**。开发时留下的截图是核对用的；别人打开线上看到的和图对不上，就会困惑。
  发出去只给一种格式。
- **改了产品的结构或分类名，同一轮把介绍页和教程列进改动清单**，和产品一起交付，不等别人来提。
- **让人往系统里交东西的功能（登记、提交），默认让人对自己的 AI 说**：页面上只留一段说明（要讲清哪几样）和一段可以复制给 AI 的开场白；
  没说全的由 AI 追问，问齐了经系统的 MCP 提交；AI 自己看得出来的不问人。**审核和判断留在页面上由人点**，也不让 AI 先替审核人填建议值。

## 常见往返

- 看原型时推翻了一条产品规则 → 回产品改文档里那一条，原型跟着改，版本升一个小号。
- 开发中发现原型没定的状态 → 回 UI 补上那个状态，不在代码里自作主张。
