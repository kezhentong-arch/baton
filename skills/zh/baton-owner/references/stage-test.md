# 测试环节：边做边测，问题回开发，过了两段一起结束

验收别人交付的东西，需要完整的测试报告和问题单。负责人**自己做、自己测**时，大部分流程可以省，但下面几条不能省。

## 进来 AI 做什么

- **先列清单**：按产品定稿和原型，列出要测的行为（页面 / 状态 / 动作 → 预期）。粒度到「一条能独立判对错」；
  只写模块标题不算覆盖。
- **真的操作**：打开真实页面，走真实步骤，看真实结果。截图只证明当时的画面，不证明功能通过；
  自动化测试通过，也不能代替亲眼对照原型。
- **问题回开发**：测出的问题直接回开发环节改（两段同时开着），改完回到同一条清单项复测。
  不写问题报告、不建单；除非要分包给别人修，那时才写一份对方能照着复现的报告。
- **为具体问题加的回归测试必须能失败**：把问题放回去，它得变红；永远是绿的测试只是摆设。
- **机械的核对交给脚本**：对没对齐、页面开不开得了、只读的地方是不是真改不了、重置后数据回没回去。
- **人看着真数据提意见、AI 当场改**，这也是测试环节，和开发交替开着。每条意见先核实是不是真问题再改；人看错了的，如实指出。
- 外部审核（例如应用商店审核）不算测试，是自己控制不了的等待时间，单独记。

## 产出

- 一份清单：每条「通过 / 失败 / 阻塞 / 未测」，失败的写现象和复测结果；
- 对应的截图或回读证据，和清单放在同一个任务目录。

## 什么算做完（出口）

- 清单上每条都有结果；失败的要么已修并复测通过，要么写明为什么留着；
- 核心路径在**真实环境**（线上，或本机真跑）走过，不是只在测试数据里走过；
- **谁提的需求谁验收**：分包回来的东西由负责人验收，不由做的人自己说过了；
- 过了：测试和对应的开发一起结束（两个环节都记结束）。

## 用得上的经验

- **数据同步类功能，按「对面可能发生的每一种事」逐项问「这边看得到吗」**：新建、完成、放弃、改期、暂停、换负责人……
  逐个核，比只测「数据同步过来了」能多找出一批缺口。人问「这件事为什么这边没有」时，如实说是漏了还是有意取舍。
- **审查或测试找到一个问题，就补一条最小的回归测试**；不为凑覆盖率补。

## 常见往返

- 测出来是产品没定 → 回产品 / UI 定下来，不在测试里凑合；
- 修一处牵动别处 → 回开发，清单上相关的项全部重测，不只测改的那一条。
