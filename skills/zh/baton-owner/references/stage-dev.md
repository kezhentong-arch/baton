# 开发环节：先跑起来，自测过才算完

代码怎么写，沿用团队仓库自己的开发与测试规范。本页只写负责人带着 AI 自己做开发时多出来的几条。

## 进来 AI 做什么

- **先判归属**：这段代码属于哪个模块就放哪里；哪儿都不属于，就另开目录，不硬塞。
- **技术方案 AI 自己定**，做完一句话交代；不列选项让非技术出身的负责人选。
- **先跑起来，不做大活**：能跑、能验证优先；不为架构整洁拖工期，不搭用不上的脚手架。
- 做到一半发现产品没定的事 → 回产品 / UI 补上，不在代码里自作主张。
- 多个对话并行改同一个仓库时，各用各的工作区（例如 git worktree）；提交只带自己改的路径，不用 `git add -A`。
- **影响线上或数据的改动**（新增或删除接口、改数据结构、上线），动手前先说清三件事：改什么、为什么非改不可、改错了能不能退回去。
  人点头才做；改数据结构前先备份，先在测试环境跑通。
- **界面改动先在本地测试环境给人看，点头后再上线，上线后回读线上确认**。测试环境用数据副本，不接线上的存储、通知和外部服务；
  不要为了「看着更像线上」给它加线上凭证，否则在测试环境里的删除、上传、通知都会落到线上。
- 自己做不了的（常见的是后端、线上服务、数据迁移）分包：先把能做的跑通，再写清「缺什么」交出去（见主手册第五节）。
- 每出一个看得见的结果（页面能开、接口通了、数据拉到了），在个人看板记一条。

## 产出

- 能在本机跑起来的东西，加启动方法，加针对具体故障的最小回归测试；
- 已提交并推送到团队主线。

## 什么算做完（出口）

- **跑起来了**：真的起了服务、跑了命令，看到真实画面或结果（截图、回读）；「测试全绿」不算；
- **自测过**：主路径自己走一遍，明显的坏点已修；
- 仓库自己的检查过了（格式检查、测试、文档同步）；
- 已提交推送，别人拉得到；
- 没做完的部分写清楚，不说「基本好了」。

## 用得上的经验

- **每次改界面，都用无头浏览器截图核一遍再给人看**，小改也一样，小改同样会连带弄坏别处。
  「对没对齐」「该出现的出现了没有」这类用脚本量，比肉眼准。
- **给人看之前，先请一次独立审查**：要求它在临时数据上用浏览器实测，并给出会失败的场景。正常流程才会踩到的严重问题，自己读改动看不出来。
- **样式类小修核三项**：问题修掉了；别处没变（同一份数据起一份旧版，逐像素对比）；没改过头（该显示的照常显示）。
  每一项都要在旧版或故意改坏的版本上验一次「确实会报错」。
- **同一条规则在两处各有一份实现时**，动手前两边都搜一遍；要求两边结果一字不差的，拿同一批输入两边各算、逐个比对，不靠举几个例子。
- **做给别人用的东西**（样例、工具）：数据要能离线用、不绑具体的人；交出去之前在临时目录里模拟对方的电脑完整跑一遍；
  工具每升一版，都以对方的身份再走一遍。
- **屏蔽浏览器自带操作**（滑动返回、缩放、右键）只加在需要它的页面，别写进共用样式；加之前把从这页点进去的子页面过一遍。
- **改分类名时旧记录不改写**，读的时候按对照表换成新名字；历史留痕不动，老数据和新规则也不打架。
- **攒着、稍后才同步出去的改动**，同一处只留一条没同步的，再改就覆盖它。设计时先问一遍「同一处连改两次会怎样」。

## 常见往返

- 自测发现问题 → 还在开发环节，直接改；
- 测试环节退回的问题 → 回开发改，改完再测（两段都开着，照实记）。
